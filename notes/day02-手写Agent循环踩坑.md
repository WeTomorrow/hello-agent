# 手写一个 Agent 循环，我踩了两个坑

这两天在学 Agent 开发。目标很明确：**不用 LangChain，只用 Python + DeepSeek API，手写一个最小可运行的 Agent**。

150 行，跑起来了。记录两个最有价值的发现。

---

## 一、Agent 到底是什么

不是框架，就是一个循环：

```python
messages = [system, user]

while True:
    resp = 模型(messages)                    # 把整段历史发出去
    if 没有 tool_calls:                       # 模型认为可以答了
        输出答案
        break

    for 每个 tool_call:                       # 模型要求调工具
        结果 = 执行工具()
        messages.append(结果)                 # 结果塞回历史
```

核心认知：**Agent 的"记忆"就是一个不断变长的 list。**

- 第一轮：2 条（system + user）
- 调了一次工具：4 条（多了 assistant 和 tool）
- 两个工具并发：5 条（一个 assistant 带两个 tool_call，两个 tool 结果）

没有魔法，没有向量数据库，没有记忆模块。就是 list 在长。

## 二、坑一：`description` 写不好，模型根本不调工具

加了一个天气工具，`description` 随手写：

```json
"description": "获取当前天气"
```

问它「合肥今天天气怎么样」——**它直接开口编**，压根没调工具。

改成：

```json
"description": "查询指定城市的当前天气，包括天气状况和气温。当用户询问某地天气、气温、是否下雨时使用。"
```

同一个问题，立刻调用了。

**结论**：模型的工具选择**完全依赖这段文字**。它不是"看懂了你的代码"，它只看得见 `description`。你的函数写得再漂亮，说明写得含糊，等于没有这个工具。

同理，参数说明也容易写错。我一开始把 `city` 的说明写成"当前天气"（写成了工具的功能描述，不是参数的），模型就会以为这个格子要填天气描述。

## 三、坑二：提示词自相矛盾

我写了这样一套规则：

```
4. 拿到工具结果后，用中文简洁地回答用户。
5. 无论用户用什么语言提问，你都只能用英文回答。
```

第 4 条说中文，第 5 条说英文。

结果它选了英文——**后写的那条赢了**。

但真正的问题不是"它选哪个"，而是：

> **只要提示词里存在矛盾，线上表现就会时好时坏。**

而你会误以为是"模型不稳定"，去调温度、换模型、加 few-shot，全是白费。

工程上的正确做法：**先消除矛盾，不要让模型替你权衡。**

## 四、一个意外发现：并行工具调用

问「帮我查一下合肥和北京的天气」，输出是这样的：

```
=== 第 1 轮：把 2 条消息发给模型 ===
  -> 模型请求：get_weather({"city": "合肥"})
  <- 工具返回：晴，22°C
  -> 模型请求：get_weather({"city": "北京"})
  <- 工具返回：多云，18°C

=== 第 2 轮：把 5 条消息发给模型 ===
```

两个工具在**同一轮**里调完了，所以第二轮是 5 条消息，不是 6 条。

对比之前问「算一下 23×47+8，再告诉我现在几点」——那是分两轮的（2 → 4 → 6），因为它得先拿到计算结果，才知道下一步要不要问时间。

**规律**：

- 任务**互相独立** → 可以并行，省一轮请求
- 任务**有前后依赖** → 只能串行

这个区别在工程上很关键：能并行的地方串行了，延迟和成本都会翻倍。

## 五、还有一个测试上的教训

我想验证"提示词矛盾会导致行为不一致"，于是问它「帮我算一下 23×47+8」。

两次输出完全一样：`23*47+8 = 1089`。

**但这个测试是无效的**——数字没有语言，中文说 1089，英文也说 1089，根本无法暴露差异。

换成「你好，请用一句话介绍你自己」，立刻现形。

> 一个测试，如果不能区分两种假设，它就是白做的。这比写错代码更隐蔽，因为程序不报错，你只是"以为验证过了"。
